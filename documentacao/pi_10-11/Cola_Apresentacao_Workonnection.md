## Slide 06 — Arquitetura em Nuvem — MVC + Camada de Serviços & Integrações `[Guilherme]` (`1 min 15s`)

**Bater o Olho (3 segundos):**
- 3 Camadas Cloud: Frontend SPA (React 19 na Vercel), API REST (Spring Boot 3.5 em Docker na Render) e Banco NoSQL (MongoDB Atlas).
- Por que MVC + Service Layer? Evitamos 'Fat Controllers': Controllers finos (só recebem pedidos); o Service guarda todas as regras e transações.
- 4 SDKs Externos: Pusher (chat WebSockets), Cloudinary (arquivos na nuvem), Google OAuth 2.0 e JavaMail.

**Fala Natural Sugerida:**
> *"Na nossa arquitetura em nuvem, separamos com muito rigor as responsabilidades usando o padrão MVC reforçado por uma Camada de Serviços. Na interface, temos uma Single Page Application em React 19 com TypeScript hospedada na Vercel. No backend, nossa API em Java 17 com Spring Boot roda em container Docker na Render. Aqui evitamos o antipadrão dos 'Controladores Gordos': nossos Controllers são finos, apenas recepcionam as requisições REST, enquanto a Camada de Serviços centraliza toda a lógica de negócio, as regras de permissão e o envio de feedback. Na persistência, usamos o MongoDB Atlas NoSQL, ideal para armazenar os documentos dinâmicos dos quatro perfis e expirar vagas vencidas com índice TTL nativo, somado a quatro SDKs de nuvem: Pusher para chat em tempo real, Cloudinary para comprovantes, Google OAuth e JavaMail."*

**Tradução rápida / Dica de Palco:** SPA = Single Page Application (não recarrega a tela). DTO = objeto de transferência de dados seguro. TTL = Time To Live (expiração automática no MongoDB).

## Slide 07 — SOLID & Regras de Negócio — Como o Código Blinda o Feedback `[Paulo]` (`1 min 20s`)

**Bater o Olho (3 segundos):**
- Princípios SOLID: DIP (Inversão de Dependência via Spring IoC / Repository), SRP (Responsabilidade Única) e ISP (Contratos segregados).
- Blindagem Anti-Ghosting na API (Quadro da Direita):
- 1. Recusa silenciosa direta = BLOQUEADO com erro HTTP 400 no método atualizarStatus.
- 2. Recusa construtiva = método recusarComFeedback exige motivo e dicas (HTTP 422 se vazio).
- 3. Contratação com Feedback = método enviarFeedback registra avaliação bilateral e encerra a vaga em transação única.

**Fala Natural Sugerida:**
> *"No backend, adotamos os princípios SOLID para garantir um código desacoplado e auditável. Com o princípio DIP, da Inversão de Dependência, nossos Services dependem exclusivamente de interfaces e abstrações gerenciadas pelo Spring, e não de drivers concretos do banco de dados — o que nos permitiu criar mocks precisos com Mockito. E no quadro à direita mostramos a nossa maior conquista técnica: o feedback obrigatório não é uma simples trava visual no frontend que qualquer um burla pelo Postman — ele é blindado no coração da API! Se alguém tentar alterar o status de uma candidatura diretamente para RECUSADO, o método atualizarStatus intercepta e rejeita com código HTTP 400. A recusa só é autorizada através do endpoint especializado recusarComFeedback, exigindo justificativa sob pena de erro HTTP 422. E na contratação, o enviarFeedback armazena a nota mútua e já encerra a vaga de forma atômica."*

**Tradução rápida / Dica de Palco:** DIP (Inversão de Dependência) = depender de abstrações/interfaces e não de classes concretas, viabilizando testes unitários sem precisar ligar o banco real.

**Bater o Olho (3 segundos):**

- 3. Gráficos JaCoCo: Salto de 34,5% para 88,86% (57 testes), Controllers em 100% e trava mínima (Quality Gate) de 70% no pom.xml.
- 4. Docker: Multi-stage build enxuto (imagem non-root e flag JVM 75%) e docker-compose.yml rodando local em 1 comando.

**Fala Natural Sugerida:**
> *"Para assegurar estabilidade contínua, estruturamos uma esteira completa de DevSecOps. Começamos com a especificação em BDD, escrevendo 22 cenários em Gherkin cobrindo todos os fluxos críticos. No GitHub Actions, implementamos uma pipeline de CI/CD que executa automaticamente a cada Pull Request: ela faz varredura de segurança com Gitleaks para impedir o vazamento de segredos, compila o frontend React e instancia um container temporário do MongoDB 7 para rodar a suíte de testes. Observem no gráfico o salto expressivo: elevamos a cobertura de 34,5% para quase 89% auditada pelo JaCoCo, com 100% de cobertura nos Controllers e um Quality Gate no pom.xml que bloqueia o merge se a cobertura cair abaixo de 70%. Além disso, containerizamos o backend em Docker com multi-stage build e limite de memória em 75% da RAM para operar perfeitamente nos 512 MB da nuvem."*

**Tradução rápida / Dica de Palco:** JaCoCo = plugin que audita a cobertura exata de código testada. Multi-Stage Build = técnica Docker que compila na imagem pesada e gera uma imagem final enxuta.

## Escudo Rápido — Perguntas Prováveis da Banca

### 1. Por que vocês escolheram um banco NoSQL (MongoDB Atlas) em vez de um banco relacional SQL?
- **Resposta direta:** Porque o nosso cadastro possui 4 perfis com campos bem diferentes (Estudante, MEI, ME e Empresa). No modelo de documentos do MongoDB, acomodamos subperfis polimórficos dentro de Usuario sem precisar de dezenas de tabelas e JOINs, além de aproveitarmos índices TTL nativos para expirar vagas vencidas automaticamente.

### 2. Como o sistema impede que o contratante digite apenas um espaço em branco para burlar o feedback obrigatório?
- **Resposta direta:** A validação ocorre em dupla camada (Frontend React e Service Layer no Spring Boot). Se tentarem mudar o status direto para RECUSADO, o método atualizarStatus bloqueia com erro HTTP 400. Já o endpoint recusarComFeedback valida se o motivo principal e o conteúdo foram preenchidos de fato, devolvendo HTTP 422 caso estejam vazios ou inválidos.

### 3. Onde exatamente vocês aplicaram o princípio DIP (Inversão de Dependência) do SOLID?
- **Resposta direta:** Na comunicação entre a Camada de Serviços e a Camada de Persistência. Nossos Services (como VagaService e CandidaturaService) nunca instanciam classes concretas do driver do MongoDB; eles dependem apenas de abstrações/interfaces (VagaRepository, CandidaturaRepository) injetadas pelo container IoC do Spring, o que também permitiu simular o banco com Mockito nos 57 testes.

### 4. Se o MongoDB não tem chave estrangeira com ON DELETE CASCADE igual ao SQL, como funciona a exclusão em cascata da LGPD?
- **Resposta direta:** Nós implementamos essa orquestração diretamente no UsuarioService: quando o titular solicita a exclusão definitiva da própria conta, a camada de serviço executa uma rotina coordenada que apaga as vagas daquele autor, suas candidaturas, interações, feedbacks e histórico de conversas nas 5 coleções.

### 5. Como vocês resolveram o limite de apenas 512 MB de memória RAM no deploy gratuito da Render?
- **Resposta direta:** Usamos Docker Multi-Stage Build: compilamos o projeto em uma imagem Maven/JDK pesada, mas descartamos tudo isso e levamos apenas o .jar final para uma imagem enxuta Eclipse Temurin JRE 17 rodando sem privilégio root e com a flag -XX:MaxRAMPercentage=75.0, impedindo que o Java estoure a memória do container.

### 6. Como funciona a trava de qualidade de 70% na pipeline CI/CD?
- **Resposta direta:** Configuramos a regra jacoco-check dentro do ciclo Maven verify no GitHub Actions. Hoje estamos com 88,86% de cobertura de linhas. Se qualquer novo Pull Request adicionar código sem testes e derrubar a média abaixo de 70%, a esteira reprova automaticamente antes de permitir o merge.
